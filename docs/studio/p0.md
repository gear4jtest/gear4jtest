# Gear4J Studio — P0

Prototype expérimental du 27 septembre 2026. Ce guide décrit ce qui est implémenté, sans promettre le périmètre du produit final.

## Démarrage

Prérequis : **JDK 17 complet** (compilation des chaînes), accès aux dépendances Gradle. Node 24.15+ pour les tests frontend ; aucun Node nécessaire pour exécuter les applications. CI : Node 24.19.0.

Depuis la racine du dépôt, dans un terminal local :

```bash
export GEAR4J_STUDIO_TOKEN="$(openssl rand -hex 24)"
printf '%s\n' "$GEAR4J_STUDIO_TOKEN"
# Capture visible réservée à des données synthétiques :
export GEAR4J_STUDIO_CAPTURE=synthetic
./gradlew :gear4jtest-studio-demo:runStudio
```

Ouvrir `http://127.0.0.1:8787` et saisir le token affiché dans le terminal. Dans un autre terminal avec les mêmes variables :

```bash
./gradlew :gear4jtest-studio-spring-demo:runStudio
```

Ouvrir `http://127.0.0.1:8788`. Les deux serveurs exposent aussi `/embedded`, un portail utilisant exactement le même composant public et ses événements. Un `GEAR4J_STUDIO_VIEWER_TOKEN` facultatif, différent du token éditeur, donne uniquement READ.

Les serveurs écoutent sur IPv4 loopback. Ce sont des transports de démonstration locale : ne pas les exposer comme une authentification de production. Le token reste en mémoire du navigateur et n'est pas inscrit dans son stockage ni journalisé par Studio. L'hôte déduit l'acteur de l'authentification ; le JSON ne peut pas imposer un auteur.

## Parcours livré

1. Découvrir le catalogue réel de l'application et ses contrats.
2. Valider `trim → uppercase`, enregistrer le draft, lancer le test avec `  electric  ` : résultat `ELECTRIC` si la capture synthétique est activée.
3. Ajouter un préfixe, modifier son paramètre et sauvegarder une nouvelle révision. Chaque test référence une révision enregistrée ; l'édition invalide les résultats de validation affichés.
4. Ajouter un choix GEL, par exemple `input == "ELECTRIC"`, et sélectionner les opérations des deux branches.
5. Générer le XML canonique ; l'importer explicitement dans un nouveau draft. Le XML non pris en charge est refusé.
6. Reprendre un draft par son identifiant tant que le serveur tourne. Consulter ses révisions par l'API.
7. Tester une ressource référencée : le sélecteur n'offre que les références autorisées et le run ne capture aucun payload.

Le stockage est **uniquement en mémoire**. Redémarrer supprime drafts, révisions et reçus de tests. P0 ne réalise aucune publication TEST ni promotion RUN.

## Architecture

| Module | Responsabilité |
| --- | --- |
| `gear4jtest-studio` | Modèle déclaratif neutre, catalogue public, diagnostics, révisions, provenance des runs, SPI d'autorisation/capture, service en mémoire |
| `gear4jtest-studio-runtime` | Catalogue applicatif explicite, adaptateur XML, validation/compilation/exécution Gear4J |
| `gear4jtest-studio-demo` | Hôte Java sans Spring, opérations synthétiques, HTTP/JSON local, client et composant web publics |
| `gear4jtest-studio-spring-demo` | Hôte Spring réutilisant `Gear4jSpringConfiguration`, les mêmes déclarations, le service et l'interface |

Aucun changement des sources du cœur ou du générateur existant. Le SPI de management n'expose ni Spring, ni XML, ni Jackson. L'adaptateur reçoit un `AssemblyLineExecutor` et un `ResourceFactory` appartenant à l'application ; seul son ordonnanceur de délai lui appartient. Les opérations paramétrées sont des instances fraîches/prototypes : `StationParameter` est mutable.

Les tests du module runtime réutilisent l'hôte Java comme fixture **test-only**, sans cycle de dépendance de production. Le test Java vérifie l'absence de Spring du classpath. Les tâches Maven des deux démonstrateurs sont désactivées ; les deux bibliothèques Studio suivent les conventions expérimentales du dépôt.

`SpringStudioApplication.start(...)` retourne un hôte `AutoCloseable` qui possède son serveur HTTP et son contexte Spring. Le lanceur ferme les deux à l'arrêt ; un échec de démarrage ferme aussi les ressources déjà créées.

## Sous-ensemble assumé

- Schéma déclaratif v1 : séquences, choix GEL unique `if/else` avec une opération par branche, enveloppe IN/OUT String. L'éditeur conserve l'identité des nœuds lors du réordonnancement.
- Classes d'opérations publiques de premier niveau : le générateur actuel produit des imports invalides pour des classes imbriquées. L'inscription au catalogue les refuse explicitement dans P0.
- Catalogue explicite, sans scan/exposition brute du classpath. Une déclaration commune porte métadonnées, classes, contrats, getters, références autorisées et capability TEST.
- Paramètres String déclarés ou références de ressources. Seuls les getters enregistrés peuvent devenir des références Java générées ; aucun Java arbitraire ni appel Java dans les conditions.
- Compatibilité Java vérifiée par assignabilité. `DataContract` conserve le vocabulaire COMPATIBLE / INCOMPATIBLE / UNKNOWN. P0 ne prouve pas la compatibilité des schémas métier : les métadonnées de schéma produisent un avertissement UNKNOWN_SCHEMA.
- Draft structuré invalide sauvegardable : opération inconnue sans paramètre, paramètre obligatoire absent, GEL invalide, chaîne vide. Les contrôles de sécurité et de taille continuent de s'appliquer.
- Origines STUDIO et XML_IMPORT explicites. Les chaînes programmatiques observables mais non éditables restent à intégrer ; P0 ne prétend pas sérialiser tout le runtime.

XML est un adaptateur, pas le modèle conceptuel Studio. Le round-trip est sémantique dans le sous-ensemble couvert. Les valeurs littérales et leurs blancs sont conservés ; commentaires et présentation sont normalisés. Attributs/éléments inconnus, namespaces supplémentaires, types de valeurs non pris en charge, getters arbitraires, DTD et entités externes sont refusés. Il n'y a pas d'import partiel silencieux.

La vue XML est générée à la demande et l'import crée un nouveau draft. L'édition bidirectionnelle continue et la sauvegarde de XML brut mal formé appartiennent à P2.

## Révisions et tests contrôlés

Une révision possède un UUID, un numéro relatif au draft, un auteur, une date, une origine et une définition immuable. Une sauvegarde exige `expectedRevision` ; un conflit renvoie 409. P0 réserve le draft et les reçus à leur créateur. Ce modèle minimal ne remplace pas les futurs domaines/ACL.

Le test passe par les validateurs, générateur, compilateur, classloader et injecteur existants, puis le véritable moteur Gear4J. La validation compile sans instancier les opérations ni les exécuter. Le test est une **exécution réelle**, pas une simulation ou un environnement isolé.

Un `requestId` généré par le client identifie le test. Même clé + même contenu : même reçu, pas de nouvelle exécution ; contenu différent : conflit. Un GET retrouve le reçu après une réponse perdue. Le client ne retente pas automatiquement un POST. Le serveur retient une empreinte HMAC avec clé éphémère, et non l'input brut ou son simple hash.

Le reçu distingue RUNNING, COMPLETED, PREPARATION_FAILED et OUTCOME_UNKNOWN : une erreur après un démarrage possible n'est pas assimilée à une absence d'effets. Cette protection contre les doublons s'arrête au redémarrage. Un reçu introuvable après redémarrage ne prouve pas que l'opération n'a jamais eu lieu.

Le run expose : identifiants de requête et d'exécution Gear4J, draft/révision exacts, auteur, contexte applicatif, build fourni par l'hôte, mode TEST, empreinte du catalogue, SHA-256 de l'artefact XML canonique, statut, timestamps et étapes. L'empreinte du catalogue inclut les déclarations exécutables et le bytecode des classes d'opérations ; les dépendances applicatives exigent toujours un identifiant de build fiable. Le label du démonstrateur est un label de prototype.

Limites : 64 drafts, 64 révisions par draft, 128 reçus, 16 nœuds de premier niveau, 16 paramètres par opération, 4 096 caractères par paramètre, 24 000 caractères cumulés de paramètres/conditions, input de test 8 192 caractères, requête HTTP/XML 65 536 octets. Une compilation/exécution par adaptateur à la fois. Le délai de 10 secondes demande une annulation coopérative ; il ne peut pas arrêter de force une opération qui ignore l'annulation.

## Données sensibles

Capture désactivée par défaut : `GEAR4J_STUDIO_CAPTURE=none`. `masked` conserve un remplacement fixe ; `synthetic` autorise les payloads pour une démonstration synthétique. Une erreur de redaction, une décision nulle ou une valeur capturée trop grande ferme la capture. Toute référence de ressource, y compris dans une branche non exécutée, supprime les captures IN/OUT de la chaîne entière.

Un paramètre de ressource conserve une référence autorisée ; l'application résout la valeur. Littéral dans un champ de ressource, référence non autorisée ou paramètre non classifié : refus avant stockage. Il s'agit d'une politique fondée sur le manifeste de l'application, pas d'un détecteur universel de secrets dans les champs TEXT. L'hôte doit correctement classifier ses paramètres et ses métadonnées.

Les exports contiennent uniquement définition et références autorisées. P0 ne conserve aucun input/output d'étape, message/stack d'exception, log ou contexte d'exécution. Diagnostics et erreurs utilisent des codes sans valeurs sensibles. Les règles de logs Gear4J existantes sont conservées ; les extensions/logs applicatifs et l'opt-in explicite aux détails restent sous responsabilité de l'hôte. Les inputs transitent nécessairement dans le navigateur, la requête et le runtime ; non capturable ne veut pas dire jamais reçu par l'opération.

## Contrat HTTP de démonstration

Toutes les routes API sont authentifiées ; les capacités runtime sont distinctes des permissions utilisateur. Les refus restent appliqués côté serveur. Les champs JSON inconnus, doublons de clés et valeurs supplémentaires sont refusés.

| Route | Usage |
| --- | --- |
| `GET /api/context` | Contexte, actions autorisées, exemple |
| `GET /api/catalog` | Descripteurs enregistrés |
| `POST /api/drafts` | `{definition}` |
| `GET /api/drafts/{id}` | Révision actuelle |
| `PUT /api/drafts/{id}` | `{expectedRevision, definition}` |
| `GET /api/drafts/{id}/revisions` | Historique |
| `POST /api/validate` | `{definition}` |
| `POST /api/export` | XML de `{definition}` |
| `POST /api/import` | `{source}`, nouveau draft |
| `POST /api/drafts/{id}/tests` | `{revision, requestId, input}` |
| `GET /api/tests/{requestId}` | Reçu de test |

Un nœud opération porte `kind: "operation"`, `id`, `operationId`, `parameters: {name: {kind: "TEXT" | "RESOURCE_REFERENCE", value}}`. Un choix porte `kind: "choice"`, `id`, `branchId`, `condition`, `whenTrue`, `whenFalse`. Ce transport est expérimental ; le contrat neutre est `StudioRuntime`/`StudioAuthorization`.

## Composant intégrable

Servir ensemble `studio-client.mjs` et `studio-element.mjs` depuis les ressources du démonstrateur. L'hôte rend `<gear4j-studio></gear4j-studio>` et fournit son authentification :

```javascript
import { StudioClient } from './studio-client.mjs';
import './studio-element.mjs';
await document.querySelector('gear4j-studio').configure({
  client: new StudioClient({baseUrl: '', tokenProvider: () => hostToken})
});
document.addEventListener('studio:revision', event => hostOnRevision(event.detail));
document.addEventListener('studio:run', event => hostOnRun(event.detail));
```

Les événements exposent les identifiants et l'état, sans payload de run. Shadow DOM isole les styles et les données utilisateur passent par des nœuds texte. `/embedded` démontre ce contrat. Les panneaux catalogue/éditeur/test ne sont pas encore des packages indépendants.

## Vérification et suite

```bash
./gradlew spotlessApply
./gradlew :gear4jtest-studio:check :gear4jtest-studio-runtime:check \
  :gear4jtest-studio-demo:check :gear4jtest-studio-spring-demo:check
./gradlew check
```

Le check du démonstrateur installe les dépendances de développement verrouillées avec `npm ci --ignore-scripts` et teste client + interactions DOM. Les seuils de couverture antérieurs restent inchangés. Consulter [verification.md](verification.md) pour les résultats exacts et les limitations de l'environnement.

Le scénario navigateur facultatif est `gear4jtest-studio-demo/src/test/browser/flow.cjs`. Après démarrage des deux hôtes, avec les tokens synthétiques explicités dans le script : `cd gear4jtest-studio-demo`, `npm ci`, `npx playwright install chromium`, puis `node src/test/browser/flow.cjs`. Il ne doit pas être confondu avec les tests DOM exécutés.

P1 : stockage durable, domaines, ownership, ACL, audit et authentification applicative. P2 : grammaire complète, vrais contrats métier, import plus large et provenance des chaînes programmatiques. P3 : publication TEST, promotion RUN et versions. Control plane, activation/deployment, SSE durable et simulation restent différés. Le prototype ne fige pas la technologie frontend ni le protocole de management final.

# Gear4J Studio P3 — versions, publication TEST et promotion RUN

P3 prolonge le [management P1](p1.md) et l’[authoring P2](p2.md). Elle utilise
le cycle existant d’`AssemblyLineManager` ; elle n’introduit ni activation,
ni DeploymentBinding, ni Application/Target, ni orchestrateur distribué.
Le correctif P2 des révisions SOURCE est inclus.

## Démarrer et essayer le cycle

Extraire les sources dans un répertoire propre. Utiliser un JDK 17 complet et,
pour les vérifications frontend, Node 22.22.2+, 24.15+ ou 26+ et npm.

```sh
export GEAR4J_STUDIO_TOKEN="$(openssl rand -hex 24)"
export GEAR4J_STUDIO_VIEWER_TOKEN="$(openssl rand -hex 24)"
export GEAR4J_STUDIO_DB_FILE="/chemin/absolu/studio-p3-java"
./gradlew :gear4jtest-studio-demo:runStudio
```

Ouvrir `http://127.0.0.1:8787`, saisir le token éditeur, créer un domaine,
une chaîne et un draft. Enregistrer puis valider une définition, tester la
révision, saisir un libellé tel que `1.0.0` et **Figer une version**. Sélectionner
la version pour consulter son XML exact, la tester, **Publier en TEST**, puis
**Promouvoir en RUN**. Le composant indique le résultat observé pour chaque mode.
Le contenu figé devient accessible aux lecteurs de la chaîne, même si le draft
source est privé : le formulaire le signale avant la création.

La démo Spring utilise `:gear4jtest-studio-spring-demo:runStudio` et le port 8788.
Lui attribuer un autre fichier H2. `/embedded` consomme les mêmes composants
publics. La capture est désactivée par défaut ; `GEAR4J_STUDIO_CAPTURE=synthetic`
permet d’observer les sorties pour des données de démonstration synthétiques.
Aucun appel à un registre Maven/npm ni déploiement externe n’est nécessaire.

**Base neuve requise pour cette version expérimentale.** Les migrations V1 H2
et PostgreSQL sont consolidées avant la première release, conformément au choix
du projet. Ne pas réutiliser un fichier P1/P2, effacer sa table de migrations,
ou supprimer automatiquement les données. Garder les anciennes bases ; une
reprise de données existantes doit être une migration explicite, contrôlée.

## Modèle et invariants

| Objet | Rôle |
| --- | --- |
| Draft / Revision | Travail modifiable et snapshots immuables STRUCTURED ou SOURCE. Une révision structurée peut encore être sémantiquement invalide. |
| StudioVersion | Candidat immuable issu d’une révision STRUCTURED validée : chaîne, draft/révision exacts, identité Gear4J, libellé, auteur/date, contexte/build/catalogue, media type, XML UTF-8 exact et SHA-256. |
| StudioPublication | Intention et résultat durable pour `(versionId, TEST ou RUN)` ; ces deux modes sont indépendants. |
| ControlledRun | Provenance du test : révision, éventuelle version Studio/libellé, artefact exact, catalogue/build réellement utilisés, acteur, identifiant d’exécution et captures autorisées. |

Le libellé est unique par chaîne, immuable, limité à 64 caractères
`[A-Za-z0-9][A-Za-z0-9._-]*`. `latest` est réservé. Une nouvelle définition exige
une nouvelle version. Deux versions peuvent référencer la même révision.
La création d’une version valide, exporte et fige le contenu ; elle ne publie pas.
Une SOURCE n’est jamais convertie implicitement par cette action, même si son
texte serait analysable. Il faut prévisualiser, appliquer et enregistrer une
révision structurée. Aucune version n’est créée en cas d’échec de validation.

L’historique est paginé du plus récent au plus ancien par date puis UUID, avec
un curseur lié à une version de cette chaîne. Chaque requête revérifie l’ACL.
La comparaison utilise les révisions immuables et les XML figés, sans régénérer
une ancienne version avec le catalogue courant. La lecture JDBC vérifie le hash.

## Publication synchrone et reprise

Les APIs restent synchrones. Seule l’intention de publication et son résultat
sont persistés, car la transaction de management et celle du moteur ne sont
pas une transaction atomique commune.

1. Sous verrou de domaine : revérifier les droits, écrire REQUESTED et l’audit
   dans la même transaction. Ne pas maintenir cette transaction pendant la compilation.
2. Appeler `registerAssemblyLine(..., TEST, ...)` ou `promoteTestToRun(...)`.
3. Relire l’objet Gear4J et vérifier identité, version, mode, media type, taille
   et empreinte contre l’artefact figé.
4. Enregistrer le résultat et son audit atomiquement.

| État | Signification et suite |
| --- | --- |
| REQUESTED | Demande durable ; appel en cours ou interrompu. Actualiser pour relire Gear4J. |
| CONFIRMED | L’artefact exact a été observé dans ce mode. Un nouvel appel identique n’effectue pas une nouvelle publication. |
| REJECTED | Politique refusée, publication TEST préalable absente, ou conflit d’artefact identifié. Corriger la configuration/politique puis reprendre explicitement si pertinent. |
| UNKNOWN | Résultat indéterminé, y compris intention interrompue sans artefact observé. Actualiser avant une reprise explicite. |

Une réponse perdue ne provoque aucune répétition automatique de POST côté client.
`refresh` ne publie rien ; il relit le moteur et persiste l’observation. Un
REQUESTED sans artefact devient UNKNOWN et permet une reprise explicite. La clé
d’idempotence est l’identité complète de l’artefact immuable et du mode ; le SPI
impose à l’adaptateur de refuser toute substitution de contenu. La date/auteur de
la première demande sont conservés, chaque tentative est auditée sous son acteur,
et l’auteur/date de publication proviennent de l’objet réellement observé.
Une réussite est enregistrée même si l’acteur a perdu ses droits pendant l’appel ;
la réponse suivante, elle, est soumise aux droits actuels.

La promotion exige une publication TEST confirmée et relit son artefact exact.
Elle revalide les capabilities RUN via Gear4J. Elle ne crée pas une nouvelle version.
La politique RUN est un opt-in explicite du manifeste ; l’ancien constructeur de
métadonnées et l’ancienne surcharge `inferred` accordent seulement TEST lorsqu’il
est demandé, jamais RUN implicitement.

`CONFIRMED` ne signifie pas que toutes les instances ont chargé la version.
Le mécanisme `latest` et son invalidation restent ceux de Gear4J. Promouvoir une
ancienne version ne constitue pas une commande de rollback/activation garantie.
Le libellé du dépôt externe ne remplace pas automatiquement le champ `version`
de la définition DSL Java, qui peut rester à sa valeur par défaut. La provenance
Studio utilise donc les identifiants et empreintes explicites ; P4 devra conserver
cette distinction pour les exécutions observées hors Studio.

## Autorisation et données

| Cas d’usage | Permission et portée |
| --- | --- |
| Figer | READ sur le draft et READ + PUBLISH sur sa chaîne ; capability PUBLISH_TEST. |
| Lire, comparer, actualiser l’observation | READ sur chaque chaîne concernée. Comparaison limitée à une même chaîne. |
| Publier | READ + PUBLISH sur la chaîne ; capability PUBLISH_TEST. |
| Promouvoir | READ + PROMOTE sur la chaîne ; capability PROMOTE_RUN. |
| Tester un draft | READ + TEST sur le draft ; capability CONTROLLED_TEST. |
| Tester une version | READ + TEST sur la chaîne ; capability CONTROLLED_TEST_VERSION. |

Les droits d’un propriétaire de draft ne lui donnent pas la publication de sa
chaîne parente. Une chaîne/domaine archivé ne permet plus de tester, publier ou
promouvoir. Les adaptateurs restent des dépendances privées de la façade ; aucune
route ne renvoie le runtime ou le publisher. L’identité ne vient jamais du JSON.
Le publisher Gear4J refuse un acteur de plus de 200 caractères, limite native de
ses métadonnées, sans le tronquer ni le substituer.

La politique de données P2 reste appliquée avant chaque persistance. Les secrets
sont des références autorisées et non des valeurs injectées dans le XML. L’audit
contient identifiants/actions/auteurs/dates, sans définitions, payloads ni messages
d’exception fournisseurs. Les paramètres déclarés publics par l’hôte restent sa
responsabilité : le Studio ne prétend pas reconnaître un secret arbitraire dans
un champ public.

Le correctif SOURCE conserve exactement les textes admis (y compris XML invalide,
retours ligne et espaces), sans tentative de récupération partielle. Son contrôle
lexical inspecte tout le texte, même après la première erreur syntaxique. Les
valeurs impossibles à classifier, commentaires non vides, CDATA, entités externes,
attributs inconnus et certains fragments ambigus sont refusés sans persistance.
Une erreur n’efface pas le texte local. Cette admission conservatrice protège la
politique de secrets ; elle ne promet pas le stockage de tout texte arbitraire.

## APIs ajoutées

Toutes les routes ci-dessous ont le préfixe `/api/v1`. Les champs JSON inconnus
sont rejetés. Le transport des deux démos partage la même implémentation neutre.

| Méthode et route | Corps / résultat |
| --- | --- |
| `PUT /drafts/{id}/source` | `{expectedVersion, mediaType:"application/xml", source}` → draft avec révision SOURCE. |
| `POST /drafts/{id}/versions` | `{revision, label}` → VersionState, statut 201. |
| `GET /chains/{id}/versions?limit=25&after=…` | Page de VersionState. |
| `GET /versions/{id}` | VersionState : version, publications, actions actuellement autorisées. |
| `POST /versions/{id}/publish` | `{}` → état de publication TEST. |
| `POST /versions/{id}/promote` | `{}` → état de promotion RUN. |
| `POST /versions/{id}/refresh` | `{}` → observations réconciliées. |
| `POST /versions/{id}/compare` | `{otherVersionId}` → diff et XML exacts. |
| `POST /versions/{id}/tests` | `{requestId, input}` → reçu et éventuel ControlledRun. |
| `GET /tests/{requestId}` | Reçu du même acteur, sous ACL actuelle de la ressource. |

Un résultat UNKNOWN/REJECTED est un résultat métier dans VersionState, pas une
réponse HTTP qui prétendrait qu’aucune mutation n’a eu lieu. Les erreurs en amont
restent des codes sûrs (403, 404, 409, 422, 503 selon le cas).

## Intégration hôte et composants publics

`StudioPublisher` est optionnel dans `StudioManagementService`. En son absence,
l’authoring P2 continue et les capabilities de publication ne sont pas annoncées.
L’hôte fournit un `AssemblyLineManager`, ses repositories et une politique de
configuration ; `Gear4jPublicationAdapter` les utilise sans en prendre possession.
Le traducteur public `Gear4jPublicationAdapter.translator(catalog)` emploie le même
manifeste explicite que le catalogue, les retrievers et les politiques TEST/RUN.

`DemoPublicationHost` illustre un stockage externe JDBC H2 durable, partagé avec
le management. Il crée les configurations manquantes de ses propres chaînes en
DATABASE et ne remplace pas les configurations présentes. Ce provisionnement
est réservé à la démonstration embarquée ; une application réelle garde son
processus de configuration et ses policies. Les ressources et DataSource fournis
par l’hôte ne sont jamais fermés par la façade. Le propriétaire du manager le ferme.

Le paquet `distributions/gear4j-studio-web-0.3.0.tgz` ajoute le composant public
`gear4j-versions` et l’export `@gear4j/studio-web/versions`. Le workspace l’utilise
lui-même, à partir des permissions de la chaîne. Le composant accepte un client,
un chainId et éventuellement un accès au draft courant pour figer sa révision.
Voir le [guide frontend](../../gear4jtest-studio-web/README.md).

## Limites de phase

Les tests contrôlés exécutent réellement les opérations autorisées ; ils ne
constituent ni une simulation ni une isolation des effets de bord. Le codec
externe reste String → String ; les liens internes peuvent être typés différemment.
Tester une version compile son XML exact, sous les policies et le build actuels,
sans la publier. Changer un binaire d’opération peut changer son comportement :
le XML figé n’embarque pas les binaires, et le résultat indique le build/catalogue
réel. Les reçus de tests restent bornés et en mémoire ; P4 doit traiter l’historique
d’exécutions durable, les traces, métriques et le temps réel. Les scénarios
persistés, mocks/isolation, multiples applications/targets, validation d’un
reviewer obligatoire et approbation avant promotion ne sont pas introduits ici.


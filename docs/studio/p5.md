# Gear4J Studio P5 — application autonome et cibles distantes

P5 fédère les APIs de management existantes depuis une application autonome.
Chaque cible conserve son stockage, son catalogue, ses ACL, ses scénarios, ses
runs et son audit. Le Studio autonome sélectionne la cible et relaie les cas
d’usage sécurisés ; il n’exécute pas directement `StudioRuntime`.

La décision figure dans [ADR 0053](../decisions/0053-studio-federates-authoritative-management-contexts.md).
La qualification est détaillée dans [verification-p5.md](verification-p5.md).

## Clôture des deux contrats P4.1

| Remarque | Décision |
| --- | --- |
| `SYNTHETIC_TEXT` transformable par le SPI | **D’accord.** Le chemin était trop permissif. La policy autorise/refuse à la sauvegarde et avant le test ; Studio exécute directement `ScenarioInput.value()` persisté, espaces et retours à la ligne compris. Le résolveur n’est jamais appelé. |
| Empreinte du contenu externe | **D’accord sur la provenance, partiellement sur la garantie.** Une empreinte permet de constater une dérive ; elle ne rend pas le fournisseur immuable et ne permet pas de reconstruire le contenu. Studio conserve maintenant référence, version et empreinte du contenu effectivement exécuté, sans sa valeur. |

`ScenarioDataPolicy.resolveFixture` remplace `resolveInput`. Il retourne un
`ResolvedScenarioInput` construit par `hmacSha256(value, keyId, secretKey)`.
L’empreinte est calculée sur `UTF8("gear4j-scenario-input-v1\0") || UTF8(value)` ;
aucune normalisation n’est appliquée. La fabrique accepte du texte Unicode
valide de 8 192 caractères Java au plus. Elle lie l’empreinte à la valeur :
le provider ne peut pas fournir arbitrairement un digest distinct.

Un SHA-256 public faciliterait les essais de valeurs prévisibles. Le HMAC utilise
une clé secrète stable détenue par l’hôte, idéalement 256 bits générés aléatoirement,
jamais stockée dans une chaîne ou dans un run. `keyId` identifie sans ambiguïté
la clé et sa génération ; le changer à chaque rotation. Deux empreintes ne sont
comparables que pour le même `keyId`, selon la résistance cryptographique du HMAC.
L’empreinte reste une métadonnée de corrélation, pas une anonymisation.

La provenance `ResolvedFixture` est écrite dès l’admission du run et conservée
avec le résultat. Sa lecture exige aussi READ et READ_SCENARIOS sur le scope du
scénario. L’audit ne reçoit ni valeur, ni référence de fixture, ni empreinte.
Les IN/OUT d’un test par référence restent non capturables. Une dérive du
contenu ou une rotation de clé change l’identité du reçu : même requestId,
contenu différent donne CONFLICT pendant sa fenêtre d’idempotence.
Un nouveau requestId peut exécuter la nouvelle valeur ; aucun catalogue global
d’empreintes attendues n’est introduit.

Le fournisseur reste responsable de la disponibilité et de l’immuabilité de
`(reference, version)`. La démo emploie une clé éphémère avec un nouvel identifiant
à chaque démarrage : comparaison possible dans un même processus seulement.
Un hôte réel fournit sa clé stable via son mécanisme de secrets.

## Modules et responsabilités

| Module / composant | Responsabilité |
| --- | --- |
| `gear4jtest-studio-http` | Adaptateur HTTP public de la façade management : routes, DTO stricts, identité fournie par l’hôte, snapshots SSE embarqués. Aucun serveur ni authentification imposés. |
| `gear4jtest-studio-standalone` | Annuaire configuré, délégation des credentials, adaptateur distant borné, application locale autonome et distribution Gradle. |
| `@gear4j/studio-web/targets` | `FederationClient` et `gear4j-targets`, qui emploient le même workspace public que les applications embarquées. |
| Application cible | Authentification, identité courante, catalogue/capabilities, ACL, politiques de données, transactions, audit et exécution Gear4J. |

`StudioApplication(id, name)` est un regroupement d’affichage. Un
`StudioTarget(id, applicationId, name, runtimeContextId, endpoint)` désigne un
contexte management stable. Un environnement peut être représenté par une cible
nommée ; cela ne change pas le sens Gear4J de TEST/RUN. Les IDs d’application,
de cible et du contexte sont distincts, explicites, et jamais déduits d’une URL.

`TargetDirectory` est une configuration immutable, limitée à 32 applications et
32 cibles. Les identités de contexte doivent être uniques dans cet annuaire.
Le contexte reste ancré dans la base de chaque application. Le catalogue peut
évoluer dans le même contexte ; les règles existantes de version et fingerprint
continuent de s’appliquer. Pas de base centrale dupliquant les ressources, ni
de CRUD de targets, ni de découverte du réseau.

La visibilité d’une cible est une permission locale d’accès au point d’entrée.
Elle ne confère **aucun** droit sur ses chaînes. Les IDs de ressources, curseurs
et requestId restent dans leur espace de cible ; aucune recherche ou liste ne
mélange implicitement deux contextes.

## Contrat distant et authentification

Le navigateur reçoit seulement des IDs et libellés de cibles autorisées via
`GET /studio/api/v1/targets`. Il appelle ensuite
`/targets/{targetId}/api/v1/...`. L’URL distante ne vient jamais du navigateur.
L’annuaire est une allowlist administrée ; seules les routes management connues
sont relayées. HTTPS est obligatoire sauf `http://127.0.0.1` pour les démos
locales. URLs avec credentials, fragments, query, chemins encodés ou `..` sont
refusées. Les endpoints n’ont pas de slash terminal. Un préfixe de chemin exige
un reverse proxy cible qui le retire avant le handler `/api/v1`.

`TargetCredentials` fournit un bearer propre à l’acteur et à la cible. L’hôte
peut relayer le token utilisateur si son audience le permet ou effectuer son
échange habituel. La cible authentifie ce credential elle-même. Aucun header
`actor`, aucune copie de groupes et aucun compte technique administrateur ne
remplacent cette authentification. Les deux hôtes doivent convenir d’un subject
stable ; des subjects divergents sont refusés plutôt que mappés silencieusement.

Avant chaque action, l’adaptateur distant relit `/api/v1/context` et vérifie :

- `X-Gear4J-Management-Protocol: 1` ;
- `X-Gear4J-Runtime-Context` et le contexte de la réponse ;
- le subject réellement authentifié par la cible.

Il transmet aussi `X-Gear4J-Expected-Context` et `X-Gear4J-Expected-Subject`
(subject UTF-8 encodé Base64URL sans padding). Le handler les revérifie **sur
l’appel effectif**, avant l’opération management. Ces headers contraignent une
identité déjà authentifiée ; ils ne donnent aucun droit. Une cible incompatible
échoue sans mutation. L’annuaire est revérifié après la lecture du contexte.
La sécurité reste framework-neutral ; l’adaptateur Spring d’identité existant
reste utilisable et le core Gear4J ne dépend pas du transport.

Le client fédéré lie également ses appels au RuntimeContext de l’inventaire
sélectionné via Expected-Context. La passerelle vérifie cette précondition avant
le relais : un changement de configuration après redémarrage ne peut rediriger
silencieusement les saisies d’un ancien workspace vers un autre contexte.

L’hôte du handler fournit serveur, executor borné, TLS, politique d’origine/CSRF
et authentification. L’adaptateur ne les configure pas à sa place. Les serveurs
de démonstration et le launcher autonome écoutent uniquement sur loopback,
contrôlent Host/Origin, utilisent des bearers explicites et aucun cookie.
Un déploiement partagé avec SSO/ingress doit intégrer ces contrats au transport
de l’organisation ; ce launcher n’est pas un serveur Internet avec SSO intégré.

## Bornes et réponses incertaines

Valeurs de l’adaptateur distant : 8 opérations simultanées, 15 s par échange
HTTP (handshake puis action), requête JSON 64 Kio, réponse 1 Mio. Concurrence
configurable entre 1 et 32, délai entre 50 ms et 2 minutes. Le provider de
credentials est synchrone et doit être borné par l’hôte. Le serveur local a
8 workers et une file de 32 ; le transport d’un hôte partagé doit aussi borner
les lectures entrantes et le nombre de connexions.

Les réponses dépassant la borne sont annulées pendant leur lecture. Pas de
redirect HTTP, ni de propagation de cookies, de pages HTML ou de détails
d’exception. Aucun retry applicatif automatique. Le publisher du corps HTTP
refuse une seconde émission, y compris si le client HTTP tente un retry PUT.

Une coupure, un délai ou une réponse invalide **après envoi d’une mutation**
produit `REMOTE_OUTCOME_UNKNOWN`. Cela ne signifie ni échec ni annulation du
métier. La cible peut encore terminer. Procédure de reprise :

- Test : relire le reçu avec le même requestId, puis le journal durable des runs.
  L’idempotence du reçu reste locale, TTL/LRU, et ne survit pas au redémarrage.
- Publication/promotion : relire la version ; demander le refresh explicite
  pour réconcilier avec le stockage Gear4J. Les attemptId P3 restent locaux.
- Sauvegarde ou création : relire la ressource/liste et son audit avant une
  éventuelle nouvelle action ; aucune promesse d’exactly-once distribuée.

Les SSE distants ne sont pas relayés en P5 : la route events retourne 501 et le
composant public utilise son polling de snapshots durables. Pas d’event log
central. La révocation d’accès est contrôlée sur chaque requête ; les données
affichées sont retirées lorsqu’un refus de contexte/identité/accès est observé.

## Navigation et composants

L’utilisateur choisit application/cible. Chaque sélection crée un nouveau
`ManagementClient` et un nouveau `gear4j-workspace`. Les anciennes réponses de
connexion ne peuvent remplacer la cible choisie ensuite. Les saisies du draft,
du scénario, des formulaires et des ACL protègent le changement de cible ; une
action en cours bloque ce changement. L’abandon reste explicite. Une connexion
échouée à une nouvelle cible laisse le workspace précédent disponible.

Le token reste en mémoire du bootstrap, sans localStorage, URL ou export.
Déconnexion explicite et retrait du composant arrêtent le suivi des runs.
`studio:target` expose uniquement targetId/runtimeContextId ; `studio:disconnect`
permet à l’hôte de vider sa session. Aucune valeur de fixture dans ces événements.

## Lancement avec deux applications réelles

Prérequis : JDK 17, le wrapper du projet, Node conforme au package web pour les
tests UI. Les commandes suivantes partent de la racine du dépôt. Configurer
dans les trois terminaux les mêmes deux variables secrètes
`GEAR4J_STUDIO_TOKEN` et `GEAR4J_STUDIO_VIEWER_TOKEN`, différentes, de 24 à 512
caractères. L’exemple utilise les sujets `demo-editor` et `demo-viewer` reconnus
par les applications Java/Spring. Les tokens ne figurent pas dans les properties.

Terminal Java :

```sh
export GEAR4J_STUDIO_DB_FILE="$PWD/studio-data/p5-java"
./gradlew :gear4jtest-studio-demo:runStudio
```

Terminal Spring, **autre base** :

```sh
export GEAR4J_STUDIO_DB_FILE="$PWD/studio-data/p5-spring"
./gradlew :gear4jtest-studio-spring-demo:runStudio
```

Terminal Studio autonome :

```sh
./gradlew :gear4jtest-studio-standalone:installDist
gear4jtest-studio-standalone/build/install/gear4jtest-studio-standalone/bin/gear4jtest-studio-standalone \
  gear4jtest-studio-standalone/example.properties
```

Ouvrir `http://127.0.0.1:8790`. L’éditeur voit Java (8787) et Spring (8788), le
viewer voit Java seulement. Chaque cible possède ses propres domaines. Créer
un domaine, une chaîne `text_preparation`, un draft, puis un scénario
`demo/greeting` version `1`, résultat attendu SUCCEEDED/HELLO. Tester, figer une
version, publier TEST et promouvoir RUN. Changer de cible montre un autre
catalogue/contexte et un autre espace de ressources.

`distZip` produit aussi la distribution avec launchers Unix/Windows, dépendances
et example.properties. Le fichier UTF-8 est strict : clés inconnues, annuaires
ambigus, tokens absents ou utilisateurs dupliqués sont refusés. Les credentials
distants se configurent par utilisateur/cible via des noms de variables
d’environnement. Les changements de cette configuration nécessitent un
redémarrage ; le SPI d’un hôte peut appliquer une politique dynamique.

## Compatibilité et suite

Le schéma JDBC P4.1 n’est pas modifié. L’empreinte est un champ optionnel des
documents JSON existants ; les runs historiques n’acquièrent aucune provenance
inventée. Une base P4.1 peut être conservée avec le même RuntimeContext. Ne pas
ouvrir la même base avec les démos Java et Spring. Ne pas supprimer une base
pour changer de cible. Le guide P4.1 conserve sa consigne historique pour P4 → P4.1.

Changements d’API expérimentale : `ScenarioDataPolicy.resolveInput` devient
`resolveFixture`, les records de run/provenance gagnent un champ fixture, et
`RequestActorContext` passe de `studio.demo` à `studio.http`. Les imports des
hôtes sont mis à jour. `ManagementRoutes` et sa suite HTTP ont également quitté
demo. **Extraire cette archive dans un dossier propre**, ou supprimer les trois
anciens fichiers déplacés avant de superposer les sources :

- `gear4jtest-studio-demo/src/main/java/io/github/gear4jtest/studio/demo/ManagementRoutes.java` ;
- `gear4jtest-studio-demo/src/main/java/io/github/gear4jtest/studio/demo/RequestActorContext.java` ;
- `gear4jtest-studio-demo/src/test/java/io/github/gear4jtest/studio/demo/StudioHttpServerTest.java`.

Le frontend passe à 0.5.0 ; son archive consommable figure dans `distributions/`.
Le mode embarqué reste utilisable sans registre de cibles et sans standalone.
Activation/DeploymentBinding, desired/observed, distribution d’artefacts entre
cibles, rollback orchestré et haute disponibilité centrale restent différés
jusqu’à un besoin explicite. Le `latest` Gear4J et TEST/RUN ne changent pas.
P6 reste la simulation (dry-run, mocks, isolation) ; aucune promesse d’isolation
d’un test contrôlé n’est ajoutée par P5.

# Gear4J Studio — P1 : fondations de management

État du 28 septembre 2026. Cette phase remplace le stockage temporaire des hôtes P0 par un espace de travail durable : domaines, chaînes, drafts, révisions, partage, autorisations et audit. Elle conserve le sous-ensemble d’édition et les tests contrôlés de P0. Publication TEST, promotion RUN, versions publiées et observabilité de production restent en P3/P4.

## Démarrer

JDK 17 complet, dépendances Gradle accessibles ; Node 24.15+ uniquement pour les tests du frontend (CI : 24.19.0). Aucun Node requis au démarrage des applications.

```bash
export GEAR4J_STUDIO_TOKEN="$(openssl rand -hex 24)"
export GEAR4J_STUDIO_VIEWER_TOKEN="$(openssl rand -hex 24)"
printf 'Éditeur : %s\nLecteur : %s\n' "$GEAR4J_STUDIO_TOKEN" "$GEAR4J_STUDIO_VIEWER_TOKEN"
# Facultatif : capturer uniquement des données synthétiques de démonstration.
export GEAR4J_STUDIO_CAPTURE=synthetic
./gradlew :gear4jtest-studio-demo:runStudio
```

Ouvrir `http://127.0.0.1:8787`. L’autre hôte démarre avec `./gradlew :gear4jtest-studio-spring-demo:runStudio` et écoute sur `http://127.0.0.1:8788`. Les deux proposent `/embedded`, qui utilise les mêmes composants publics.

Chaque hôte crée une base H2 fichier, respectivement `studio-data/java` et `studio-data/spring`, relativement au répertoire du processus. `GEAR4J_STUDIO_DB_FILE` permet de choisir un chemin absolu **sans extension**. Utiliser un fichier différent pour chaque processus ; ne pas partager une base H2 fichier entre les deux hôtes. Le mot de passe local peut être fourni par `GEAR4J_STUDIO_DB_PASSWORD`. Sans configuration, la base locale a un mot de passe vide ; protéger les fichiers et leurs sauvegardes par les droits du système hôte.

Le token éditeur correspond au sujet `demo-editor`, membre du groupe `domain-creators`. Le token lecteur correspond à `demo-viewer`, sans aucun accès initial. Le libellé « lecteur » ne constitue pas un rôle imposé : les permissions effectives viennent des ACL. Ces tokens démontrent l’intégration locale, pas une authentification de production. Ils ne sont ni persistés dans le navigateur ni journalisés par Studio. Les routes n’acceptent jamais un acteur, des groupes ou un statut administrateur dans le corps d’une demande.

## Parcours vérifiable

1. Créer un domaine `catalog`, puis une chaîne `vehicles`, puis un draft. Son état initial contient l’exemple `trim → uppercase`.
2. Modifier et enregistrer le draft, même si sa définition est incomplète ou invalide. Les configurations interdites par la politique de ressources restent refusées.
3. Valider, puis tester une révision enregistrée avec `  electric  `. Avec capture synthétique : `ELECTRIC`. Le test conserve les identifiants exacts de la révision et du catalogue.
4. Ouvrir « Gérer les accès », ajouter USER / `demo-viewer` / READ. Dans un autre navigateur avec le second token, le draft apparaît et reste en lecture seule. Accorder séparément EDIT, VALIDATE ou TEST si souhaité.
5. Consulter les révisions et repartir d’une ancienne révision dans un nouveau draft privé. Consulter l’audit pour voir les auteurs et les changements d’accès.
6. Redémarrer le même hôte avec la même base : domaines, chaînes, drafts, révisions, ACL et audit sont conservés. Les reçus et résultats des tests restent temporaires.
7. Abandonner un draft ou archiver une chaîne/un domaine : l’historique reste accessible selon les droits, les modifications et nouveaux tests sont bloqués.

Les listes sont paginées après filtrage des autorisations. Les modifications non enregistrées d’un draft exigent un abandon explicite avant changement de sélection. En cas de conflit, le client ne renvoie pas automatiquement la modification ; l’utilisateur doit recharger et reprendre son changement.

## Modèle et limites

| Objet | Contrat P1 |
| --- | --- |
| Domain | UUID, clé unique globale, nom, description, propriétaire, état, dates, version de concurrence |
| Chain | UUID, domaine, clé unique dans le domaine, documentation, propriétaire, héritage des droits, état, dates, version |
| Draft | UUID, chaîne, nom, propriétaire, héritage, état, numéro de tête, origine, éventuelle révision de départ, dates, version |
| Revision | UUID, draft, numéro croissant dans le draft, auteur, date, origine, définition déclarative immuable |
| ACL | Héritage facultatif et autorisations explicites de sujets USER, GROUP ou AUTHENTICATED |
| AuditEvent | Identité, auteur, action, périmètre, ressource, version, date, révision/requête éventuelles, politiques d’accès avant/après |

La **version de concurrence de la ressource** change après modification des métadonnées, ACL, état ou définition. Le **numéro de révision du draft** change uniquement quand une nouvelle définition est enregistrée. Les mutations exigent `expectedVersion` : envoyer le numéro de révision à sa place est incorrect.

La définition persistée est le modèle déclaratif Gear4J sérialisé en JSON par un adaptateur fermé et versionné (`schemaVersion: 1`). Elle n’est pas dérivée d’un XML persistant. L’export XML reste sémantique ; les constructions inconnues sont refusées à l’import. Une empreinte SHA-256 détecte une corruption accidentelle du document stocké ; elle ne protège pas contre un administrateur de base malveillant.

`STUDIO` et `XML_IMPORT` indiquent l’origine du draft ; une reprise conserve l’origine et référence exactement sa révision de départ. Le registre des chaînes Java observables sans être éditables reste en P2/P4. Aucun modèle de publication, d’activation ou de déploiement n’est ajouté artificiellement à P1.

Clés et propriétaires sont immuables dans cette phase. Pas de transfert de propriété, déplacement entre domaines, suppression physique, restauration après archivage, commentaires ni édition collaborative en temps réel. Repartir d’un draft abandonné reste possible dans une chaîne active si les droits le permettent.

## Autorisations

L’hôte fournit `CurrentActorProvider`, dont la valeur est une `StudioIdentity` : sujet stable, groupes vérifiés, éventuel rôle d’administration. Une identité absente est refusée. Le droit global de créer un domaine est une politique explicite injectée dans le service ; il n’est pas accordé à tous les utilisateurs par défaut.

- Les droits sont des autorisations positives cumulatives ; aucun DENY implicite ou explicite. USER et GROUP se cumulent, AUTHENTICATED utilise le sujet `*`.
- READ implique DISCOVER. DISCOVER seul expose un identifiant, un nom et une référence parente, sans définition, description, propriétaire ou révision. Le nom est donc une métadonnée volontairement découvrable.
- Consulter une définition exige READ. Modifier, tester, valider, gérer les accès ou créer un enfant exige également READ sur le périmètre concerné, en plus de l’action spécifique. L’audit nécessite DISCOVER et READ_AUDIT ; il n’accorde pas la lecture des définitions.
- Une chaîne hérite des droits du domaine à sa création. Un draft est privé par défaut : son héritage est désactivé. Les bénéficiaires d’une ACL du parent ne peuvent donc pas automatiquement consulter ce draft.
- Le propriétaire d’une ressource, le propriétaire de son domaine et l’administrateur fourni par l’hôte ont les droits de gestion. Un draft privé n’est **pas** privé vis-à-vis du propriétaire du domaine ou de l’administrateur. Le propriétaire d’une chaîne n’a pas de privilège automatique sur les drafts privés d’autres personnes, sauf s’il est aussi propriétaire du domaine.
- L’archivage retire EDIT, CREATE_CHAIN, CREATE_DRAFT, VALIDATE, TEST et ARCHIVE aux descendants concernés, y compris aux propriétaires. La lecture et la gestion des ACL restent possibles.
- Une ressource non découvrable renvoie NOT_FOUND ; une action refusée sur une ressource découvrable renvoie FORBIDDEN. Listes et audit filtrent aussi chaque enfant ; le droit d’audit d’un domaine ne dévoile pas les événements de drafts privés.

La permission utilisateur et la capacité du runtime restent distinctes. Autoriser TEST ne crée pas la capacité CONTROLLED_TEST. L’API vérifie les deux et l’éditeur tient compte des capacités annoncées.

Une révocation bloque les demandes suivantes et les écritures encore en attente du verrou transactionnel. Elle n’annule pas une exécution déjà admise et ne peut pas retirer une réponse déjà reçue par le navigateur. Aucun cache d’autorisation inter-requêtes n’est utilisé.

## Transactions et persistance

Le SPI `StudioStore` ne dépend ni de JDBC, ni de Spring. `JdbcStudioStore` fournit un adaptateur H2/PostgreSQL. Le module réutilise le migrateur Gear4J existant avec un identifiant de module indépendant `gear4j-studio` et ses propres tables `g4js_*` ; les tables runtime/publication ne sont pas modifiées.

Chaque lecture utilise un snapshot REPEATABLE_READ. Une mutation ouvre une transaction READ_COMMITTED, verrouille la ligne du domaine, relit les droits et l’état, applique le compare-and-set de version, puis enregistre ses révisions/ACL/audit dans la **même transaction**. Un échec de l’audit annule la mutation. Le verrou par domaine simplifie la cohérence des révocations héritées ; il peut limiter le débit des écritures dans un très gros domaine. Aucun verrou n’est conservé pendant une compilation ou une exécution de test.

Le service garde le contrôle des mutations et des audits ; le SPI de stockage est destiné au code de confiance de l’hôte, pas aux contrôleurs exposés directement. Les sessions ne peuvent pas être conservées hors du callback. L’adaptateur emprunte des connexions avec auto-commit actif, crée sa transaction, ferme la connexion empruntée et **ne ferme jamais la DataSource**. Une connexion déjà engagée dans une transaction hôte est refusée. Avec un pool, utiliser ses connexions habituelles ; ne pas injecter une connexion transactionnelle partagée.

Tables : `g4js_resource`, `g4js_domain`, `g4js_chain`, `g4js_draft`, `g4js_revision`, `g4js_acl`, `g4js_audit`. Index de périmètre et contraintes d’unicité protègent clés et numéros de révision. Les UUID fournissent une pagination stable sans offset. L’audit utilise une séquence ; les trous dus aux rollbacks sont normaux. Il est durable et append-only par le service, pas WORM face à un administrateur SQL.

Les migrations V1 se trouvent dans `gear4jtest-studio-jdbc/src/main/resources/io/github/gear4j/studio/db/`. L’hôte peut les appliquer avec son outil de migration au lieu du démarrage automatique du démonstrateur. PostgreSQL possède un test Testcontainers dédié ; son exécution dépend de Docker, voir le bilan de vérification.

## Intégration Java et Spring

```java
StudioJdbcSchema.migrate(dataSource, Gear4jDatabaseDialect.POSTGRESQL);
CurrentActorProvider actors = hostSecurity::currentStudioIdentity;
var service = new StudioManagementService(
    new JdbcStudioStore(dataSource), applicationRuntime, actors,
    identity -> identity.groups().contains("domain-creators"));
```

`hostSecurity` représente le mécanisme d’authentification vérifié de l’application. L’hôte choisit les groupes et le statut administrateur ; jamais un champ envoyé par le navigateur. `applicationRuntime` implémente le SPI `StudioRuntime` ou utilise l’adaptateur Gear4J local.

Dans Spring, enregistrer ces objets comme beans. Le démonstrateur utilise un `RequestActorContext` borné à la requête HTTP et nettoyé en `finally`, la même `StudioManagementService` et une DataSource fournie par l’hôte. L’intégration ne requiert pas Spring Security. Pour une application qui l’utilise, un bean `CurrentActorProvider` peut lire `SecurityContextHolder`, refuser l’authentification absente/anonyme, puis convertir le principal et les autorités validées en `StudioIdentity`. Ce mapping reste applicatif : Studio ne suppose ni nom de claim JWT, ni fournisseur d’identité, ni convention de rôles. P1 ne livre pas de starter de connexion à un IdP.

Le transport JDK HTTP fourni est local et démonstratif. Les applications peuvent exposer le service dans leurs propres contrôleurs sécurisés et utiliser le client web public. Une infrastructure de production doit fournir son authentification, sa protection des sessions/CSRF si elle emploie des cookies, les restrictions réseau et la gestion des fichiers/secrets adaptés à son environnement.

## APIs du démonstrateur

Préfixe unique `/api/v1`. Les anciens endpoints P0 `/api/*` ne permettent plus de contourner les ACL.

| Méthode et chemin relatifs | Contrat |
| --- | --- |
| GET `/context`, `/catalog` | Identité courante, capacités, politique de création, catalogue explicite |
| GET `/domains`, `/chains`, `/drafts` | `{items,nextCursor}`, paramètres `parent`, `after`, `limit` (1–100) |
| POST `/domains` | `{key,name,description}` |
| POST `/chains` | `{domainId,key,name,description}` |
| GET `/resources/{id}` | `{resource,kind,permissions}` |
| PUT `/resources/{id}` | `{expectedVersion,name,description}` ; description vide pour un draft |
| GET `/resources/{id}/access` | `{version,policy,permissions}` lus dans un seul snapshot |
| PUT `/resources/{id}/access` | `{expectedVersion,policy:{inheritAccess,grants:[{subjectType,subject,permissions}]}}` |
| POST `/resources/{id}/archive` | `{expectedVersion}` ; abandon pour un draft |
| GET `/resources/{id}/audit` | Page d’événements autorisés ; `after` est une séquence |
| POST `/drafts` | `{chainId,name,definition}` |
| GET `/drafts/{id}` | `{draft,revision,permissions}` |
| PUT `/drafts/{id}` | `{expectedVersion,definition}` ; nouvelle révision |
| GET `/drafts/{id}/revisions` | Page de révisions ; `after` est un numéro |
| POST `/drafts/{id}/fork` | `{revision,name}` ; nouveau draft dans la même chaîne |
| POST `/import` | `{chainId,name,source}` ; XML vers nouveau draft |
| POST `/resources/{id}/validate`, `/export` | `{definition}` ; validation ou XML canonique dans un périmètre autorisé |
| POST `/drafts/{id}/tests` | `{revision,requestId,input}` ; exécution de cette révision |
| GET `/tests/{requestId}` | Reçu accessible à l’acteur initial, sous réserve du READ actuel sur le draft |

Erreurs publiques sans détails internes : 400 demande invalide, 401 non authentifié, 403 refus, 404 invisible/absent, 409 conflit, 422 définition/configuration refusée, 429 capacité, 503 stockage indisponible. Aucun retry automatique de mutation. En cas de rupture réseau ou d’erreur de commit, relire l’état : l’absence de confirmation n’établit pas l’absence de commit. L’audit permet de retrouver la mutation.

## Composants publics

Le workspace et l’éditeur sont les composants utilisés par l’application elle-même. Servir les quatre modules `studio-client.mjs`, `management-client.mjs`, `studio-element.mjs`, `studio-workspace.mjs` ensemble.

```javascript
import { ManagementClient, ScopedAuthoringClient } from './management-client.mjs';
import './studio-workspace.mjs';
const client = new ManagementClient({tokenProvider: () => hostToken});
await document.querySelector('gear4j-workspace').configure({client});
// Éditeur seul, si le portail fournit sa navigation :
const state = await client.draft(draftId);
const scoped = new ScopedAuthoringClient(client, state, await client.context());
await document.querySelector('gear4j-studio').configure({
  client: scoped, revision: scoped.flat(state)
});
```

Les événements `studio:revision` et `studio:run` transmettent des identifiants et états, pas les payloads. Le portail qui utilise l’éditeur seul doit gérer la navigation, la fermeture avec saisie non enregistrée et l’actualisation des ACL. Les sous-panneaux ne sont pas encore publiés séparément sur npm.

Le service `InMemoryStudioService` et `StudioClient` P0 restent des fixtures expérimentales autonomes pour le prototype et ses tests. Les deux applications livrées utilisent exclusivement `StudioManagementService`, `ManagementClient` et le stockage JDBC. Aucun endpoint P0 n’est conservé dans les hôtes P1.

## Données et tests contrôlés

Aucun input/output de test, log, stacktrace ou message d’exception n’est stocké dans l’audit P1. Les événements ne recopient pas les définitions ou les métadonnées libres. Les anciennes ACL sont conservées pour expliquer les changements d’accès ; READ_AUDIT donne donc accès à leurs bénéficiaires historiques.

Les secrets de configuration restent des références autorisées dans les définitions. La politique applicative de classification des paramètres, de capture et de redaction de P0 reste applicable. Une description, un nom, un identifiant de bénéficiaire ou un paramètre TEXT n’est pas un champ de secret : aucun détecteur universel ne peut garantir la suppression d’un secret volontairement collé dans un champ libre. Les fixtures et scénarios persistants ne font pas partie de P1.

`TEST_REQUESTED` est audité durablement avant l’appel runtime. Il prouve une admission, **pas une exécution achevée**. Les reçus RUNNING/COMPLETED/PREPARATION_FAILED/OUTCOME_UNKNOWN restent en mémoire, avec déduplication par identité de requête et empreinte HMAC. Une même clé ne relance pas le test pendant la vie du processus. Après redémarrage, un reçu absent ne prouve pas l’absence d’effets : ne pas relancer automatiquement. La persistance des runs arrive en P4 ; aucun workflow distribué ou flux d’événements durable n’est ajouté ici.

Les limites de grammaire P0 restent : String → String, séquences et choix GEL avec une opération par branche, 16 nœuds, 16 paramètres/opération, 4 096 caractères/paramètre, 24 000 caractères cumulés ; input de test 8 192 caractères, corps HTTP 65 536 octets. P1 retire les quotas mémoire de drafts/révisions ; les listes sont paginées. 64 bénéficiaires explicites par ACL, 128 reçus de test par service vivant. Une exécution à la fois par adaptateur local ; délai coopératif, sans isolation de processus.

# Gear4J Studio P4 — exploitation et observabilité

Note historique : [P4.1](p41.md) remplace le chemin synchrone d’observation, le
verrou de domaine par mise à jour et le groupement par nodeId seul. Son guide
fournit le raccordement actuel du dispatcher et la maintenance de fraîcheur.
Les scénarios annoncés ci-dessous sont maintenant implémentés en P4.1.

Statut : implémenté dans les modules expérimentaux Studio. La qualification et
ses limites sont décrites dans [verification-p4.md](verification-p4.md).
Cette phase prolonge [P3](p3.md), sans introduire de control plane distribué.

## Réévaluation de P3

| Point | Avis et décision |
| --- | --- |
| Reçus des tests contrôlés | D’accord. TTL terminal de 30 minutes et LRU sous pression, capacité par défaut 128, configurable. Un RUNNING ne peut être ni expiré ni évincé. La garantie d’idempotence est limitée à la présence du reçu : au plus le TTL, éventuellement moins sous pression. Réutiliser un identifiant expiré peut exécuter un nouveau test ; les clients ne répètent jamais automatiquement un POST. |
| Tentatives de publication | D’accord. Chaque tentative a un UUID durable et audité. Complétion et refresh comparent cet UUID sous verrou de domaine. Un refresh compare aussi le snapshot de départ ; une observation ancienne ne peut rétrograder un état plus récent. Aucun workflow générique ajouté. |
| Catalogue TEST/RUN | D’accord. Une capacité logique possède un contrat/documentation et des bindings par mode. Classes et getters peuvent différer. Les signatures Java résolues doivent correspondre ; les schémas métier restent une déclaration de l’hôte, pas une preuve obtenue par réflexion. Le fingerprint comprend les deux implémentations et leurs getters. |
| Scénarios persistés | Partiellement d’accord : le report était insuffisamment explicite. Ils sont déplacés vers **P4.1 — scénarios réutilisables**, après le socle d’observation P4 et avant les travaux P5/P6. Ce lot n’est pas implicitement couvert par les reçus ou l’historique des runs. |
| Provenance du format | Partiellement d’accord. Les octets exacts restent l’autorité, mais expliquer leur génération nécessite aussi la version du modèle et de l’adaptateur. Ces trois métadonnées sont désormais figées dans StudioVersion, sans mécanisme de migration automatique. |
| SOURCE invalide | D’accord sur la documentation ; aucun assouplissement. La classification conservative de toutes les valeurs reste préalable à toute persistance. |

L’adaptateur XML `gear4j-studio-xml`, version `2`, émet des références de
paramètres logiques (`parameter:prefix`). Le traducteur fourni résout le getter
du binding TEST ou RUN à la génération Java, sans modifier l’artefact publié.
Les anciens getters explicitement déclarés restent importables lorsqu’ils ne
sont pas ambigus. Ces tokens nécessitent le traducteur Studio fourni ; un
générateur XML configuré sans cet adaptateur ne doit pas les exécuter.

## Périmètre P4

- Journal JDBC durable des tests Studio, indépendant des reçus temporaires.
- Observations de runs hôtes explicitement raccordés, y compris chaînes Java
  programmatiques sans définition éditable ou version Studio attestée.
- Recherche par chaîne/draft, période bornée, statut, mode, version Studio,
  identifiant Gear4J et durée minimale ; pagination avec curseur opaque.
- Inspection des étapes, parents, branches, durées et codes d’erreur sûrs.
- Indicateurs sur les observations conservées et accessibles uniquement.
- Snapshots durables, SSE best effort, relecture après reconnexion et polling.
- Composant public `gear4j-runs`, utilisé par le workspace et intégrable seul.

Les données runtime libres, contextes, stacks et messages d’erreur fournisseurs
ne sont jamais copiés automatiquement. Les captures IN/OUT String passent par
DataCapturePolicy ; les références de ressources désactivent la capture des
tests Studio. Les valeurs non capturées restent explicitement NOT_CAPTURED.

## Démarrer

JDK 17 complet, wrapper fourni, Node/npm pour vérifier les composants.

```sh
export GEAR4J_STUDIO_TOKEN="$(openssl rand -hex 24)"
export GEAR4J_STUDIO_VIEWER_TOKEN="$(openssl rand -hex 24)"
export GEAR4J_STUDIO_DB_FILE="/chemin/absolu/studio-p4-java"
./gradlew :gear4jtest-studio-demo:runStudio
```

Ouvrir `http://127.0.0.1:8787`, saisir le token, ouvrir/créer un draft et lancer
un test. Le panneau **Exploitation** du draft retrouve les observations ; celui
de la chaîne rassemble ses runs hôtes, ses tests de versions et les tests des
drafts que l’utilisateur peut consulter. **Actualiser** recharge la base ;
**Actualiser automatiquement** active le suivi des nouvelles observations.
Choisir un run pour consulter sa provenance et ses étapes. Aucun run n’est
relancé par ce panneau. Les droits READ_RUNS et READ_OBSERVABILITY sont accordés
séparément dans le partage ; READ seul ne les implique pas.

Spring utilise `:gear4jtest-studio-spring-demo:runStudio`, port 8788 et un autre
fichier de base. `/embedded` consomme les mêmes composants publics. La capture
est désactivée par défaut. `GEAR4J_STUDIO_CAPTURE=masked` illustre la redaction ;
`synthetic` est réservé aux données de démonstration explicitement capturables.

**Utiliser une nouvelle base de développement P4, conserver les bases P3.**
Les migrations V1 H2/PostgreSQL sont consolidées avant la première release :
nouvelles colonnes de tentatives/provenance, table et index `g4js_run`.
Il n’existe pas de migration automatique ni de suppression des données anciennes.
L’identité stable du RuntimeContext reste liée à la base ; un changement de
catalogue/build sous la même identité ne réécrit pas la provenance historique.

## Journal, provenance et permissions

| Identité | Garantie |
| --- | --- |
| requestId | Reçu de test local au processus, HMAC de l’acteur/contenu/input, TTL/LRU. Ne constitue pas un historique durable ni une déduplication entre processus. |
| StudioRun.id | Identité durable de l’observation, attribuée à l’admission. Existe même si la compilation échoue avant de produire un identifiant moteur. |
| RunObservation.runId | Identité Gear4J de l’exécution effectivement commencée, nullable avant démarrage. Parents/racine et identités des étapes sont conservés lorsqu’ils sont disponibles. |
| revisionId / versionId | Provenance exacte du test. Pour un run hôte, versionId reste absent tant que l’hôte ne peut attester la correspondance exacte. Aucune résolution historique via latest. |

Admission d’un test : droits et révision exacte, audit et observation PREPARING
dans la même transaction courte. La compilation/exécution se fait ensuite hors
transaction. Les callbacks d’étapes fournissent des snapshots RUNNING ; le
résultat final est persisté après retour de l’exécuteur. Les tests de versions
conservent le build/catalogue effectivement employés, distincts de ceux qui ont
produit la version. Une erreur de préparation devient PREPARATION_FAILED ; une
issue non déterminable devient UNKNOWN, sans message fournisseur ni input brut.
Un échec de stockage après exécution donne un reçu OUTCOME_UNKNOWN, jamais une
preuve de non-exécution et jamais un retry automatique.

Les écritures d’une observation sont sérialisées sous le verrou du domaine. Le
hash d’artefact et l’identité moteur ne peuvent changer après leur attribution ;
un état terminal ne peut être écrasé par un callback RUNNING tardif. Le journal
conserve le dernier snapshot, pas chaque transition. `sequence` compte ses mises
à jour ; ce n’est ni un offset SSE ni une preuve que tous les événements moteur
ont été reçus.

Si le processus disparaît sans résultat final, la dernière observation reste
PREPARING/RUNNING. Ce statut décrit la dernière observation, pas une présence
attestée du processus. Aucun détecteur distribué, heartbeat durable ni mécanisme
de reprise de l’exécution n’est ajouté en P4.

La lecture exige READ et READ_RUNS sur la ressource d’origine. Le détail des
captures/étapes exige aussi READ_OBSERVABILITY ; à défaut l’API renvoie le résumé.
La recherche et les métriques filtrent chaque observation avec ses droits
actuels : une ACL de chaîne n’ouvre pas un draft privé. Les versions figées et
leurs tests sont partagés au niveau chaîne conformément à P3. La consultation
de métriques exige READ et READ_OBSERVABILITY. Aucun compteur privé n’est exposé.

## APIs de lecture

La façade `StudioManagementService` expose `runs`, `run` et `metrics`. Le transport
de démonstration Java/Spring illustre les routes suivantes, réutilisables dans un
transport applicatif propre. Les identités proviennent toujours de l’hôte.

| Route GET | Résultat |
| --- | --- |
| `/api/v1/resources/{chainId-or-draftId}/runs` | Page de résumés, sans captures ni étapes. |
| `/api/v1/resources/{chainId-or-draftId}/metrics` | Comptages et durées sur les observations accessibles de la fenêtre. |
| `/api/v1/runs/{observationId}` | Snapshot durable, détail selon les droits. |
| `/api/v1/runs/{observationId}/events` | Snapshots SSE best effort, mêmes contrôles d’accès. |

Runs/métriques exigent `from` inclusif et `until` exclusif en ISO-8601, sur
**createdAt** (date d’admission de l’observation), avec une fenêtre positive de
31 jours maximum. Filtres facultatifs : `status`, `mode=TEST|RUN`, `versionId`,
`runId` (identité Gear4J), `minimumDurationMillis`. Runs accepte `limit` de 1 à
100, défaut 25, et `after`. Les champs inconnus sont refusés. Un run sans durée
finale ne satisfait pas un filtre de durée minimale.

Les filtres sont appliqués en SQL avant le scan ACL, avec index chaîne/date,
statut/date, scope/date, identifiant moteur et rétention. Chaque lecture parcourt
au maximum 500 candidats. Une page vide peut donc contenir un curseur de suite.
Le curseur opaque est lié à l’acteur/groupes, au scope et aux filtres, expire
après 15 minutes et devient invalide au redémarrage du service. Il contient la
position date/UUID : la suppression de la ligne frontière ne casse pas la suite.
La pagination n’est pas une transaction figée entre plusieurs requêtes ; les
nouveaux runs apparaissent en revenant au début de l’historique.

## Indicateurs et limites de capture

Nombre par statut, minimum/moyenne/maximum et p95 des durées finales. p95 utilise
le rang supérieur `ceil(0.95 × n)` des durées triées. Série par heure jusqu’à deux
jours de fenêtre, sinon par jour UTC. Les étapes sont regroupées par nodeId dans
la chaîne, sur les versions/modes retenus par le filtre. Les 20 plus lentes et
les 20 avec le plus d’échecs sont présentées, union sans doublons. Les stations
structurelles font aussi partie des étapes ; ces durées ne doivent pas être
sommées comme des temps exclusifs.

Un résultat `partial=true` signale un scan limité ou des étapes tronquées. Les
statistiques portent uniquement sur les observations retenues/accessibles,
jamais sur un total prétendument exhaustif du moteur. Une opération hôte non
raccordée au journal n’est pas comptée. P4 n’ajoute pas de séries Prometheus,
d’agrégats pré-calculés, de SLO/alertes ni d’import automatique d’un backend de
traces ; le module Micrometer Gear4J existant reste utilisable indépendamment.

Un snapshot contient au plus 256 étapes, 8 192 caractères par capture, et
262 144 caractères JSON. Le dépassement d’étapes est signalé, jamais présenté
comme une trace complète. Seuls les IN/OUT String racine explicitement admis ou
masqués sont capturés. Les inputs/outputs par étape, objets arbitraires, logs,
messages d’exception et contextes libres ne sont pas exportés par l’adaptateur.
Les codes d’erreur sont fermés : EXECUTION_ERROR, TEST_NOT_ADMITTED,
TEST_OUTCOME_UNKNOWN. Une erreur de redaction donne NOT_CAPTURED.

## Raccorder une exécution applicative

`StudioRunRecorder` est un port **hôte de confiance**, distinct de la façade
management et sans route HTTP d’écriture. L’hôte associe explicitement son run
à une StudioChain portant le même runtimeAssemblyLineId. Ce lien rend une chaîne
Java observable sans la déclarer éditable ou exportable. Aucun accès au runtime
n’est réintroduit par `StudioManagementService`.

Extrait de raccordement (la création de la chaîne et la politique sont fournies
par l’application ; un test exécute réellement ce chemin sans Spring) :

```java
var recorder = new StudioRunRecorder(store, contextId, Clock.systemUTC());
var provenance = new StudioRun.Provenance(contextId, line.getId(), build,
        catalogFingerprint, null, "application", "RUN",
        null, null, null, 0, null, null);
UUID observationId = recorder.beginHostRun(studioChainId, provenance);
var observer = new Gear4jRunObserver(
        snapshot -> recorder.record(observationId, snapshot), capturePolicy, null, input);
var result = executor.execute(line, RunRequest.builder().input(input)
        .resourceFactory(resources).with(observer).build());
recorder.record(observationId, observer.finish(result));
```

Le constructeur sans `input` choisit NOT_CAPTURED pour l’entrée. L’hôte est
responsable de n’enregistrer que des métadonnées non sensibles, d’appliquer la
politique avant le port d’écriture et de désactiver la capture pour les runs
manipulant des secrets. Une version Studio renseignée exige le même chainId,
hash et libellé. Une version non attestée reste absente ; elle n’est pas inventée
depuis la définition Java ou depuis latest.

Les callbacks sont passifs : leur échec de stockage n’altère pas le flow moteur.
L’écriture finale est explicite pour que l’hôte traite son échec sans rejouer le
run. En cas d’exception hors résultat de l’exécuteur, l’hôte peut enregistrer un
snapshot UNKNOWN avec le code sûr TEST_OUTCOME_UNKNOWN, ou laisser la dernière
observation indéterminée ; ne jamais sérialiser l’exception brute. L’hôte conserve
la propriété de ses exécuteurs et de sa DataSource.

## Rétention et temps réel

Les reçus temporaires et les observations durables ont des politiques distinctes.
`TestReceiptPolicy` accepte une capacité de 1 à 10 000 et un TTL terminal positif
jusqu’à un jour ; défaut 128 / 30 minutes. GET/replay touche la récence LRU sans
prolonger le TTL. Tous les reçus RUNNING sont conservés, même après le TTL. Si
toutes les places sont actives, l’admission répond CAPACITY_EXCEEDED.

La rétention du journal est décidée par l’hôte :
`recorder.purgeTerminalBefore(cutoff, 100)` supprime un lot borné de résultats
terminaux anciens, jamais PREPARING/RUNNING. Il n’y a ni tâche planifiée imposée,
ni purge automatique au démarrage, ni TTL universel sur les données utilisateur.
Sans maintenance raccordée, les lignes terminales continuent de s’accumuler.

SSE relit la base toutes les secondes pendant au plus 15 secondes par connexion,
avec snapshot initial, heartbeats et revérification de l’identité/ACL à chaque
lecture. Le petit serveur embarqué réserve au plus un de ses quatre workers au
SSE ; au-delà, réponse 429 et repli frontend en polling. Cette limite est celle
du transport de démo, pas un quota global du modèle. Aucun identifiant d’événement,
replay ou journal d’événements durable. Une reconnexion relit le snapshot ;
les transitions intermédiaires peuvent ne jamais être affichées.

Le client transmet le token en header Authorization, sans paramètre URL ni
stockage local, et arrête le suivi à la déconnexion du composant. Les réponses
d’accès refusé retirent les données affichées. Le suivi ne soumet jamais de POST.
Le paquet `distributions/gear4j-studio-web-0.4.0.tgz` contient le composant public
`gear4j-runs`, également utilisé par le workspace ; voir son [README](../../gear4jtest-studio-web/README.md).

## P4.1 — scénarios réutilisables, lot prévu

Ce lot devra fournir une entrée synthétique ou une référence de fixture autorisée,
un résultat attendu facultatif, une identité/révision de scénario, sa consultation
et sa réutilisation contre une révision ou version exacte. Il s’appuiera sur les
runs durables de P4 pour conserver le résultat et la provenance du scénario testé.
L’admission des fixtures sera distincte de la capture runtime : une valeur masquée
n’est pas une fixture réutilisable équivalente, et ne doit jamais remplacer
silencieusement l’entrée originale. Aucun mock, dry-run ou isolement simulé n’est
nécessaire à ce lot. Ces derniers restent P6 ; Application/Target et contrôle
distribué restent P5.

## Limites SOURCE maintenues

La limite est de 65 536 octets UTF-8. Les balises non fermées et certaines erreurs
de grammaire sont sauvegardables si toutes les valeurs restent classifiables.
Commentaires non vides, CDATA, DOCTYPE, instructions de traitement arbitraires,
valeurs/attributs inconnus, références interdites et guillemets non fermés sont
refusés. Le scanner poursuit la classification au-delà d’une première erreur.
Les textes admis sont conservés exactement ; les textes refusés restent dans
l’éditeur local et ne sont pas présentés comme sauvegardés. Une future évolution
de cette politique devra partir de cas UX concrets et de tests de non-divulgation.

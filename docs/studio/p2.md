# Gear4J Studio P2 — authoring et consolidation

P2 conserve le socle transactionnel P1. Elle corrige les frontières nécessaires
à l’authoring, puis ajoute contrats inférés, diagnostics, prévisualisation XML,
comparaison et composants distribuables. Publication TEST et promotion RUN restent P3.

## Démarrage

Extraire l’archive dans un répertoire propre. Prévoir un JDK 17 complet ; les
contrôles frontend nécessitent Node 22.22.2+, 24.15+ ou 26+ et npm. Aucun serveur
Node n’est nécessaire pour utiliser les démos Java.

```sh
export GEAR4J_STUDIO_TOKEN="$(openssl rand -hex 24)"
export GEAR4J_STUDIO_VIEWER_TOKEN="$(openssl rand -hex 24)"
export GEAR4J_STUDIO_DB_FILE="/chemin/absolu/studio-p2-java"
./gradlew :gear4jtest-studio-demo:runStudio
```

Ouvrir `http://127.0.0.1:8787` et fournir le token éditeur défini dans ce terminal.
L’hôte Spring démarre avec `./gradlew :gear4jtest-studio-spring-demo:runStudio`
et écoute sur `http://127.0.0.1:8788` ; lui attribuer un autre fichier de base.
Les deux proposent aussi `/embedded`, qui consomme les composants publics.
Le chemin H2 est sans extension. **Choisir une base P2 neuve**, sans réutiliser
une base P1 ; voir les règles de reprise ci-dessous.

Créer un domaine, une chaîne avec son identité runtime, puis un draft. L’éditeur
permet de construire `String → Integer → String` avec les opérations de longueur
et de formatage, de valider, de comparer et de tester une révision enregistrée.
La capture d’input/output est désactivée par défaut. Pour des données de démo
exclusivement synthétiques, `GEAR4J_STUDIO_CAPTURE=synthetic` l’active au démarrage.

Le paquet frontend prêt à installer est fourni dans
`distributions/gear4j-studio-web-0.2.1.tgz` :

```sh
npm install /chemin/gear4j/distributions/gear4j-studio-web-0.2.1.tgz
```

Consulter son [guide d’intégration](../../gear4jtest-studio-web/README.md) pour
fournir l’authentification et utiliser le workspace ou l’éditeur seul.

## Invariants conservés

Management/runtime séparés ; catalogue explicite partagé avec la capability
policy ; sécurité indépendante de Spring ; acteur fourni par l’hôte et revérifié
à chaque requête. Les droits affichés par les composants ne remplacent pas les
contrôles serveur. Aucun moteur de déploiement, workflow asynchrone généralisé ou
stream durable n’est ajouté.

Draft, Revision et future Version restent distincts. Une sauvegarde ajoute une
révision immuable et un audit dans la même transaction, avec contrôle optimiste.
Un draft invalide reste sauvegardable. Une configuration interdite au stockage
ou une définition changeant l’identité runtime de sa chaîne est refusée.

Le modèle déclaratif reste indépendant du XML. Le graphe suit la grammaire
exposée par l’adaptateur ; aucun graphe libre n’est transformé implicitement en
programme Gear4J. Validation, test contrôlé et simulation restent distincts.

## Délégation

`MANAGE_ACCESS` exige aussi READ. Le délégataire ne peut ajouter ou retirer que
des droits présents dans ses `delegablePermissions`. Il peut laisser inchangé
un grant supérieur à ses propres droits, mais ne peut ni supprimer ses droits
protégés ni les déplacer vers un autre bénéficiaire.

Changer l’héritage et déléguer MANAGE_ACCESS, CREATE_CHAIN ou CREATE_DRAFT sont
réservés à l’administration complète : créer un descendant donne sa propriété,
donc son administration. La seule vérification « je possède ce droit » aurait
laissé une possibilité d’élévation indirecte.

Le propriétaire de la ressource, celui du domaine et l’administrateur hôte
conservent l’administration complète. `AccessState` expose ce statut et les
droits délégables. Les grants restent durables : révoquer les droits d’un
délégataire ne révoque pas automatiquement tous ses partages antérieurs.
L’audit les conserve ; expiration et révocation en cascade seraient un autre modèle.

## Identités, schéma et reprise

La création d’une chaîne accepte `runtimeAssemblyLineId`. Le client propose
`chain_` suivi d’un UUID sans tirets ; un identifiant explicite est également
possible. Il doit être un identifiant Java simple de 64 caractères maximum.
Il est immuable après création et unique dans la base liée au contexte, y
compris pour les chaînes archivées. Le nom d’affichage reste modifiable.

Création, import, sauvegarde, validation et export vérifient la correspondance
avec `ChainDefinition.id`. Un import ne réécrit jamais l’identité silencieusement :
créer la chaîne avec l’identité voulue ou adapter explicitement le XML.

La liaison JDBC au contexte est verrouillée lors du démarrage. L’hôte doit
configurer un identifiant stable, propre à son application logique. Deux hôtes
qui réutilisent volontairement le même identifiant sont considérés comme le
même contexte ; cette clé ne détecte pas une mauvaise configuration identique.
Changer le catalogue ne change pas le contexte : revalider les drafts avec sa
nouvelle empreinte.

**V1 pré-release est consolidée**, conformément au choix de modifier les
migrations initiales avant première release. Une base P1 existante est refusée
par la vérification de checksum ; rien n’est supprimé ni réécrit automatiquement.
Utiliser une nouvelle base de développement P2 ; le correctif SOURCE consolide également V1 et requiert une base neuve si une base P2 antérieure était déjà utilisée. Si des données P1 doivent être
conservées, préparer une migration explicite après choix des identités : une
ancienne chaîne peut avoir plusieurs `definition.id`, interdisant une conversion
aveugle qui préserverait l’immuabilité de l’historique. Ne pas contourner le checksum.

Extraire cette archive complète dans un répertoire propre. Une superposition
sur P1 peut conserver les anciens fichiers Java/JS désormais supprimés.

## Authoring, contrats et diagnostics

L’éditeur permet de découvrir les contrats et leurs origines, changer une
opération en conservant son identité, configurer ses paramètres, réordonner les
étapes et éditer un choix GEL. Les types externes peuvent être choisis parmi
ceux du catalogue explicite, sans charger une classe arbitraire.

L’analyse différée après modification ne compile pas à chaque frappe. Une réponse
ancienne ne remplace pas l’analyse d’un état plus récent. **Valider** ajoute la
compilation Gear4J réelle. **Localiser** retrouve la carte ou le champ indiqué
par le diagnostic. Un résultat avec avertissements est présenté avec réserves.

`OperatorContracts.resolve` substitue les variables à travers classes parentes
et interfaces, y compris les génériques imbriqués et tableaux. Aucun opérateur
n’est instancié et aucun scan du classpath n’est effectué. Variables non résolues,
wildcards et types effacés restent inconnus. Une déclaration explicite peut
compléter l’information absente, mais pas contredire une signature résolue.

Les formes structurelles sont déclarées par l’application : champs, contrats,
présence obligatoire et fermeture. Elles ne sont pas inférées automatiquement
des propriétés Java. Champ obligatoire absent d’une sortie fermée, champ
supplémentaire garanti face à une entrée fermée, ou type incompatible donnent
INCOMPATIBLE. Présence non garantie, générique non démontré ou schéma opaque
différent donnent UNKNOWN. Les noms de schémas ne constituent pas un validateur
JSON Schema et le compilateur ne prouve pas les règles métier.

La démo exécute réellement `String → Integer → String`. La conception et la
compilation acceptent aussi d’autres contrats externes connus du catalogue.
Les tests contrôlés de l’adaptateur local restent limités aux entrées/sorties
String : capability CONTROLLED_TEST_STRING, explication dans l’interface et
refus avant exécution. Les codecs de scénarios métier seront traités avec P3.

Grammaire v1 : séquence d’opérations et choix GEL avec une opération par branche,
les choix ayant des bornes String. Les autres conteneurs restent à prototyper
avec leur génération/compilation/exécution réelle. L’import refuse les
constructions non prises en charge. La validation compilée utilise actuellement
le profil TEST et sa capability policy ; une opération interdite dans ce profil
ne devient pas autorisée par l’éditeur.

## XML et comparaison

**Prévisualiser le XML** ne persiste rien. **Appliquer au draft courant** remplace
explicitement le modèle local ; une sauvegarde crée ensuite une révision STRUCTURED.
Ce type indique une définition représentable, pas une certification de validité :
les erreurs de contrats ou de configuration restent des diagnostics à corriger.

**Enregistrer le draft** pendant une saisie XML crée maintenant une révision SOURCE,
avec son type de média et le texte exact, sans conversion ni normalisation. Un XML
invalide reste ainsi récupérable après fermeture/rechargement. Chaque révision est
immuable, hashée, soumise au contrôle optimiste et auditée dans la même transaction.
Les ACL de lecture, modification et fork s’appliquent également aux sources.

Une révision SOURCE n’est jamais exécutée, même si son texte pourrait être valide.
Il faut prévisualiser, appliquer puis enregistrer une définition structurée ; le
test effectue ensuite sa validation habituelle. Aucune définition partielle n’est
extraite automatiquement. Le graphe n’est pas présenté pour une source non analysée.
Le diff impliquant SOURCE est textuel et l’indique explicitement.

La politique `StudioRuntime.assertSafeSourceToStore` est appelée avant toute
persistance ou copie. Son comportement par défaut refuse les sources ; l’adaptateur
local contrôle lexicalement **tout** le texte, indépendamment d’une erreur de parse.
Il applique aux valeurs les classifications et références autorisées du catalogue.
Balises non fermées, erreurs de grammaire Gear4J ou expressions invalides peuvent
être enregistrées. Les valeurs dont l’admission n’est pas démontrable sont refusées :
paramètres inconnus, références interdites, attributs ambigus/guillemets non fermés,
texte libre, commentaires non vides, CDATA, déclarations d’entités et instructions
externes. La source refusée reste visible dans l’éditeur ; elle n’est ni masquée ni
tronquée silencieusement. Cette politique conservatrice n’est pas un détecteur
universel de secrets : les champs déclarés publics restent la responsabilité du
manifest applicatif, comme dans le mode structuré.

La conversion explicite conserve sa garantie sémantique : XML → modèle → XML
canonique. Une révision SOURCE sauvegardée conserve, elle, le texte d’origine.
La comparaison d’une révision source et d’une révision structurée montre le texte
original et la projection canonique, sans annoncer de diff sémantique.

Le diff compare une révision avec le travail local ou deux révisions d’un même
draft. Les identités stables révèlent déplacements, changements d’opérations,
conditions et paramètres. Des identités dupliquées sont signalées ; le diff
utilise alors les positions sans prétendre reconnaître exactement les nœuds.

Les XML comparés sont des projections canoniques du catalogue/adaptateur courants,
pas des artefacts publiés historiques. Une définition devenue non exportable
reste comparable sémantiquement avec XML indisponible. La comparaison de futures
Versions publiées sera intégrée en P3.

## API et distribution

| Route ajoutée sous /api/v1 | Autorisation |
| --- | --- |
| PUT /drafts/{id}/source | READ + EDIT, contrôle de version et politique de données |
| POST /resources/{id}/diagnostics | READ + VALIDATE et capability |
| POST /resources/{id}/xml-preview | READ + EDIT |
| POST /drafts/{id}/diff | READ |
| POST /drafts/{id}/compare | READ |

Les scopes d’authoring désignent une chaîne ou un draft. La création d’une chaîne
reçoit `runtimeAssemblyLineId`. Le SPI runtime reste destiné à l’intégration hôte ;
la façade ne le restitue plus.

Le [package frontend](../../gear4jtest-studio-web/README.md) propose des exports
client, éditeur, workspace et ensemble des composants. Les démos Java/Spring
consomment exactement ses sources via processResources. Les tests DOM et le
contrôle du paquet font partie du check de la démo. Aucune publication npm externe.

## Pagination et limites opérationnelles

Découverte et audit parcourent au plus 500 candidats. Une page vide peut avoir
un nextCursor ; seule son absence termine le parcours. Les droits sont recalculés
à chaque page. Les continuations chiffrées et authentifiées ne révèlent pas les
identifiants des ressources invisibles, et sont liées au sujet, groupes, statut
administrateur et périmètre. Elles expirent après 15 minutes ou au redémarrage.
INVALID_REQUEST impose de repartir du début. Pas de snapshot durable entre pages.
La pagination des révisions lisibles conserve son numéro de révision comme position.

Le budget borne le nombre de candidats, pas une latence maximale indépendante
du stockage. Mesurer les ACL et optimiser leur sélection SQL avant grande échelle.
